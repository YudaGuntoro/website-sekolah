# Cendekia Dashboard project notes

- This checkout is Cendekia's school CMS.
- Frontend: `Frontend` (port 3002); API: `Backend/Cendekia.WebAPI` (port 5243).
- Local database bootstrap is `database/cendekia_cms.sql`, followed by `database/seed_cendekia_content.sql`.
- SPMB schema is `database/spmb.sql`. For existing installations run `scripts/init-local-db.ps1 -SpmbOnly` without reseeding website content.
- SPMB has exactly four date-based waves, uses WIB (Asia/Jakarta), closes outside active dates, and keeps the wave/year snapshot on each application.
- SPMB information uses typed singleton `spmb_information` (upgrade `scripts/init-local-db.ps1 -SpmbInformationOnly`) and `/spmb/informasi` admin editor. Public `/spmb` retains its timeline, fee panel, document lists, and contact footer. Year comes from the wave schedule, contacts from website_settings. `/content/spmb` redirects to the typed editor; older `school_content` spmb records are retained as archive and no longer render this page. Built-in step icon keys: register/folder/payment/test/check/book. Do not restore generic ContentSections for this page.
- Use only the `cendekia_cms` database. Schema and migration scripts describe the school CMS only.
- This repository includes the website at `../package` relative to this dashboard folder. `SCHOOL_API_URL` connects it to this API. Commit and push from the repository root; this folder is ordinary source, not a submodule or separate repository.
- Instagram/TikTok feeds use CMS collections `instagram` and `tiktok` with a dedicated `PostUrl` field. Upgrade existing databases with `scripts/init-local-db.ps1 -SocialOnly`; do not reseed existing content. Only HTTPS post URLs from the matching platform are accepted.
- Website contacts use the singleton `website_settings` table. Upgrade with `scripts/init-local-db.ps1 -WebsiteSettingsOnly`. ADMIN/SUPERVISOR may edit; the public `/api/school/contact` endpoint supplies footer, homepage contacts, and WhatsApp bubble. Blank fields stay hidden instead of falling back to old values.
- Principal greeting uses collection `sambutan`: Title is the principal name, Category is the role, Body contains all greeting paragraphs, ImageUrl is the portrait. Only the latest published entry appears in the homepage. Initialize existing installations once with `scripts/init-local-db.ps1 -PrincipalOnly`; the seed preserves any existing greeting including drafts.
- Vision, motto, and ordered mission points use singleton `school_identity`; upgrade with `scripts/init-local-db.ps1 -IdentityOnly`. Admin UI is `/settings/identity` under Profil Sekolah. CMS editor roles can save with optimistic versioning. Public `/api/school/identity` supplies desktop vision/motto/missions and mobile mission titles/content. Do not revert to hardcoded values for blank fields.
- Three homepage illustration overrides use `homepage_images`; upgrade with `scripts/init-local-db.ps1 -ImagesOnly`. Admin UI `/settings/images`, API `/api/cms/homepage-images`, public `/api/school/homepage-images`. Empty URLs and failed image loads use the original assets for hero, Arah Pendidikan, and Program Belajar. Overrides do not change per-program card images.
- Backend modules are school CMS, SPMB, LMP, authentication, and users.
- LMP means Lomba Mata Pelajaran, separate from SPMB. Public `/lmp` and `/lmp/daftar`, admin `/lmp/informasi` and `/lmp/pendaftar`, API `/api/lmp`. Initialize existing installations with `scripts/init-local-db.ps1 -LmpOnly`. Singleton `lmp_settings` uses optimistic versioning; registration closes outside inclusive WIB dates. Each class 5–6 SD participant selects exactly one of Matematika/Bahasa Indonesia/Bahasa Inggris. Private PDF files (max 2 MB) are stored in `lmp_application_documents.Content` and downloaded only through staff-authenticated endpoints, never public static URLs. Application list sorts newest Id first. Submission stores event date/title/fee snapshots, independent payment and registration statuses; no automatic payment verification. Defaults: competition 21 January 2027 07.30–16.00 WIB; announcements/gebyar 28 January 2027. Unconfirmed registration dates, document requirements, bank account and WhatsApp group remain unset/pending.
- Keep browser API calls same-origin under `/api`; local Next.js forwarding uses `API_PROXY_TARGET`.
- Keep production database credentials and signing keys in the server environment file; never commit or print them.

## Architecture and normalized schema (2026-11-06)

- Read `docs/architecture-and-database.md`. Active controllers call Application services; do not inject DbContext or use EF/SQL in controllers. Application references only Domain. Persistence implements repository and unit-of-work contracts without exposing IQueryable. Preserve row locks, optimistic versions and idempotency.
- Active schema has normalized `school_missions`, `spmb_information_steps`, `spmb_document_requirements`, `lmp_subjects`, `lmp_application_documents`, and `school_content_collections`. Singleton configuration uses typed columns. Do not restore ConfigJson/MissionsJson or the old LMP Subjects/Document columns. Historical registration snapshots are deliberate.
- Upgrade with `scripts/init-local-db.ps1 -NormalizeOnly` after stopping an old API. Existing legacy schemas are backed up automatically. Migration archives live in `schema_legacy_payloads`; they are not active configuration. Fresh bootstrap automatically migrates; repeat setup skips legacy JSON seed statements. Never run old binaries from the workspace sibling dashboard against this schema.
- `scripts/check-architecture.mjs` enforces layer boundaries. `scripts/check-normalization.mjs` tests relational constraints. Schema scripts use MySQL 8 and only the cendekia_cms database. Private backups and verification output remain under ignored `.verify-cms`.

- Registration relations v2: `academic_years` is referenced by SPMB settings and `spmb_wave_periods`. Applications reference immutable periods by composite FK `(AcademicYear,WaveNumber,WaveRevision)`; dates belong only to the period. LMP applications reference immutable `lmp_events` by EventId; event title/date/fee belong only to that event. Do not restore repeated snapshot columns on applications. API responses obtain historical values through relations. Run `scripts/init-local-db.ps1 -NormalizeOnly` (backs up pre-v2 schemas), then `node scripts/check-registration-relations.mjs`. Stop pre-v2 API binaries before upgrading. Keep unique NISN per academic year and historical facts unchanged.

## Production security

- Browser dashboard authentication uses `/api/auth/session` and a host-only HttpOnly cookie with CSRF protection. Never restore localStorage bearer tokens. Unsafe cookie requests require `X-CSRF-TOKEN` from `/api/auth/csrf`; logout revokes auth_sessions on the server. Keep non-browser bearer login compatible.
- Apply `database/auth_sessions.sql` before starting the new API (`scripts/init-local-db.ps1 -SecurityOnly` or full normalization). User role/status/username changes revoke existing sessions. Production startup must reject demo passwords and unsafe configuration. Do not weaken validation to make a production test start.
- Read `docs/deploy-vps.md` for Cendekia deployment. Keep KnownProxies explicit, CORS deny by default, rate limits on both login methods and public registrations, generic errors, and minimal readiness responses. Keep backend namespaces and assembly names under Cendekia; include only school modules.
- Security verification: `check-security.mjs`, `check-production-startup.mjs`, isolated `check-security-limits.mjs`, npm audits and NuGet vulnerability checks. Production secrets/backup/verification output stay outside Git. Actual server cron/alert configuration requires server access and must not be claimed as installed from local verification.

- Backend solution: `Backend/Cendekia.sln`. Projects are Cendekia.Domain, Cendekia.Application, Cendekia.Persistence, and Cendekia.WebAPI. Development credentials stay in ignored `appsettings.Development.json`; use the sanitized `.example.json` when setting up a new checkout.
